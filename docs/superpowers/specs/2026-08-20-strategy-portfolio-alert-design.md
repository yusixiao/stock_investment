# 策略持仓目标与买入提醒设计

## 1. 目标

在现有持仓页面上增加“策略目标持仓”能力：用户从一个已完成的回测任务创建并绑定一个账户，系统保存策略要求的股票、目标数量和参考买入价；账户只允许买入当前策略目标股票。每日市场数据更新完成后，系统读取上一个交易日收盘价，对尚未完成目标且价格跌破参考价的股票生成买入提醒事件。

本设计不实现通知渠道。提醒模块只保留一个稳定调用接口，邮件、Webhook、收件人、重试和通知渠道由后续独立任务设计。

## 2. 已确认业务规则

### 2.1 账户与策略绑定

- 一个账户最多绑定一个策略回测任务。
- 一个策略回测任务最多绑定一个账户。
- 回测任务的运行状态(`running/success/failed`)与执行状态分开；回测成功不代表正在执行。
- 当用户将任务选为执行中时，任务记录关联 `execution_account_id` 和执行状态；这只是关联元数据，不改变回测结果。
- 创建策略账户时，绑定来源 `task_id`，并以当前策略结果初始化目标持仓。
- 账户未绑定策略时，可自由买入任何股票。
- 账户绑定策略后，只限制买入股票范围：买入标的必须属于当前策略目标股票集合。
- 不限制买入价格。
- 不限制买入数量；实际数量超过目标数量时允许录入并显示超额持仓。
- 卖出不受策略目标范围限制。
- 解除绑定时保留账户交易、持仓和收益历史，归档策略目标与提醒状态，账户恢复为普通账户。
- 账户解除策略绑定时，同时清除任务的执行关联；回测任务恢复非执行状态。

### 2.2 目标持仓

- 目标持仓不是独立的真实持仓，真实持仓仍由账户交易记录推导。
- 每个目标至少包含：股票代码、目标数量、策略参考买入价、目标状态和更新时间。
- 每次策略目标都有一个生效日期；对评估日 `as_of_date`，只采用满足
  `effective_date <= as_of_date` 的最近一次目标状态。
- 如果回测任务在评估日前没有任何目标信号，则该任务没有当前策略目标；评估日之后的未来信号不能提前使用。
- 不引入执行批次概念。
- 同一股票后续调仓时更新原目标记录，不重复创建当前目标。
- 后续调仓新增股票时创建目标。
- 后续调仓删除股票时将目标数量更新为 `0`，保留历史记录。
- 目标数量为 `0` 的股票不再触发买入提醒。
- 目标变化历史需要保留，以支持审计和回溯。
- “不引入执行批次”只针对用户交互；系统内部仍保留目标生效日期，用于按时间顺序回放目标状态。

### 2.3 真实持仓与页面展示

- 用户手动录入真实交易，账户持仓、成本和收益由正常持仓逻辑计算。
- 策略目标层叠加在正常持仓页面，不另建一套策略持仓页面。
- 页面同时展示：实际持仓、目标数量、参考买入价、剩余待买数量、超额数量和提醒状态。
- 目标数量变为 `0` 但账户仍有实际持仓时，继续显示该实际持仓，标记为“策略已退出”，不触发买入提醒。
- 实际持仓完全卖出后，从当前持仓列表隐藏；已实现收益保留在交易历史和收益统计中。
- 策略目标数量不从绑定前的旧持仓推断；只有用户绑定策略后的策略账户交易才用于当前执行状态。

### 2.4 买入提醒

对每个当前目标股票计算：

```text
remaining_quantity = max(target_quantity - actual_shares, 0)
```

只有同时满足以下条件才生成买入提醒：

```text
target_quantity > 0
remaining_quantity > 0
previous_trading_day_close < reference_price
price state previously >= reference_price
```

- 价格检查使用上一个已完成交易日的收盘价，不进行盘中检查；该交易日同时作为
  `as_of_date`。例如任务 `2baab97c` 只有 `2026-06-02` 目标时，在 `2026-08-20`
  的检查仍使用 `2026-06-02` 目标。
- 每日市场数据更新成功后执行检查。
- 价格持续低于阈值时不重复生成提醒。
- 价格回到阈值或以上后重新武装；下次再次跌破时可以再次提醒。
- 目标完成后，即使价格低于参考价也不再提醒。
- 目标数量为 `0` 时不再提醒。
- 通知渠道不在本任务实现；当前模块只调用通知接口。

## 3. 推荐模块设计

### 3.1 账户模块

账户是普通持仓的唯一载体，增加可空的策略绑定信息：

```text
account
  id
  name
  strategy_task_id nullable
  strategy_bound_at nullable
  strategy_unbound_at nullable
```

`strategy_task_id` 必须唯一，保证一个任务最多绑定一个账户；账户本身最多只有一个绑定任务。

回测任务保留独立的执行元数据：

```text
execution_status       -- inactive / active
execution_account_id   -- nullable,唯一
```

这些字段只用于记录“该回测任务当前是否被某个账户执行”和历史页展示，不参与 `BacktestEngine` 的计算，也不改变任务的 `status`、`result` 或历史回测语义。

账户交易写入时：

- 未绑定策略：允许任意买入。
- 已绑定策略：只允许买入当前 `target_quantity > 0` 的股票。
- 买入数量和价格不做策略层硬限制。
- 卖出始终允许。

### 3.2 目标模块

建议将策略目标作为持仓模块内部的深模块，外部只暴露少量行为：

```python
bind_strategy(account_id, task_id)
refresh_targets(account_id, task_id)
get_current_targets(account_id)
get_target_history(account_id)
unbind_strategy(account_id)
```

内部负责：

- 读取已完成回测任务结果。
- 按策略目标生效日期顺序构建目标历史；查询当前目标时取不晚于 `as_of_date` 的最近目标状态。
- 对新增、更新、归零目标写入历史。
- 校验账户买入股票范围。

创建策略账户时，持仓模块从不可变的回测任务结果读取策略目标，并物化为自己的目标历史；回测任务本身不增加持仓字段，也不随账户持仓变化：

```text
strategy_target_history[
  {
    effective_date,
    targets: [
      { symbol, target_quantity, reference_price, status }
    ]
  }
]
```

其中 `target_quantity` 和 `reference_price` 表示策略决策要求，不是账户实际成交数量和价格。物化完成后，账户目标表与回测任务结果解耦；回测任务仍只表示“策略在各个时间点要求什么”，不关心账户当前持仓。

目标当前状态和目标变化历史分开保存。当前状态服务页面和交易校验，历史表服务审计。

### 3.3 提醒评估模块

提醒评估模块只做三个动作：

1. 读取绑定策略账户的当前目标和实际持仓。
2. 经 `DuckDBStore` 查询上一个交易日收盘价。
3. 满足条件时调用通知模块接口。

建议接口保持与通知实现解耦：

```python
class BuyOpportunitySink(Protocol):
    def emit(self, alert: BuyOpportunityAlert) -> None:
        ...
```

提醒事件至少包含：

```text
account_id
task_id
symbol
reference_price
previous_close
target_quantity
actual_shares
remaining_quantity
signal_date
valuation_date
```

本任务不规定 `BuyOpportunitySink` 的邮件实现；开发期可使用记录型 adapter 或空 adapter 测试调用链。

### 3.4 定时执行

在现有市场数据更新成功后的派生刷新流程中增加提醒评估入口：

```text
市场数据更新完成
  ↓
缓存/派生数据刷新完成
  ↓
策略买入提醒评估
  ↓
BuyOpportunitySink.emit(...)
```

提醒评估必须使用已完成的交易日数据，并且单次任务只读取 DuckDBStore，不直接读取 parquet。

### 3.5 回测历史执行状态

- 任务被账户选为执行中时，写入 `execution_status=active` 和 `execution_account_id`。
- 一个账户和一个回测任务均只能存在一个活动关联。
- 回测任务历史列表返回执行字段，并显示“执行中”标识。
- 后端列表默认排序为：执行中任务优先，其余任务保持原有 `created_at DESC` 顺序。
- 前端无论默认排序还是按收益率排序，都必须先比较执行状态，执行中任务永远位于第一组。
- 除增加执行标识和置顶外，原有任务查询、详情、删除和收益排序行为不变。

## 4. 数据来源与边界

- 策略目标初始来源：`backtest_tasks.result`；绑定账户时由持仓模块解析并物化。
- 物化后的目标当前状态和历史属于持仓模块，不回写 `backtest_tasks`，也不要求回测任务增加账户字段。
- `backtest_tasks` 只增加执行关联元数据，不保存账户持仓、目标数量或提醒状态。
- 行情来源：`DuckDBStore` 的统一查询接口。
- 真实持仓来源：账户交易记录推导，不从策略目标推导真实持仓。
- 策略目标来源：绑定回测任务结果，不从当前账户持仓反推。
- 业务数据库仍与回测、问股共享 `data/portfolio.db`，新增 schema 必须通过幂等 DDL/migration 管理。
- 不使用旧 `/api/portfolio` 作为新功能接口；新持仓 contract 继续使用 `/api/v1/portfolio` 方向。
- 不在本任务实现邮件、Webhook、通知配置或通知重试架构。

## 5. 页面行为

策略回测结果页面提供“创建策略账户/绑定账户”入口。持仓页面对绑定策略账户显示额外字段：

```text
股票
实际持仓
实际成本
当前价
目标持仓
策略参考价
剩余待买
目标状态
提醒状态
```

账户解绑后隐藏策略字段，页面回到普通账户模式；历史目标和交易记录仍可查询。
- 回测历史页对执行中任务显示执行标识，并始终置顶。

## 6. 测试范围

- 账户绑定一对一唯一约束。
- 任务运行状态与执行状态独立。
- 执行中任务在后端和前端收益率排序下都始终置顶。
- 账户绑定和解绑会正确设置/清除任务执行关联。
- 未绑定账户允许任意买入。
- 已绑定账户拒绝非目标股票买入。
- 已绑定账户允许目标股票任意价格、任意数量买入。
- 超额买入的剩余数量为零且不提醒。
- 目标数量更新、归零和重新启用。
- 目标为零但实际仍有持仓时继续显示且不提醒。
- 完全卖出后当前持仓隐藏且收益历史保留。
- 上一个交易日收盘价的查询和日期选择。
- 价格跌破、持续低于、回到阈值上方后再次跌破的提醒状态转换。
- 目标完成后不生成提醒事件。
- 提醒评估只调用 `BuyOpportunitySink`，不耦合邮件实现。

## 7. 非目标

- 不实现通知渠道和 SMTP。
- 不实现卖出提醒。
- 不把回测页面接入 Portfolio API。
- 不支持一个账户绑定多个策略或一个任务绑定多个账户。
- 不通过历史账户持仓自动推断策略执行。
